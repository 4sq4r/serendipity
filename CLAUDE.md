# Правила для Claude

Контекст проекта — в [README.md](README.md). Прочитай его перед началом работы.

## Код

- Не пиши комментарии в коде, конфигурации и скриптах сборки (Java, SQL, YAML, Gradle, Docker Compose). Код должен быть понятен без них. Если без пояснения не обойтись, сначала спроси.
- Без магических чисел и строк — именованные константы или конфигурация.
- DRY: повторяющаяся логика выносится в общие методы и классы.
- JPA-сущности не выходят за пределы сервисного слоя — наружу только DTO.
- Модули общаются друг с другом только через сервисы, не через чужие репозитории.
- Схема БД меняется только новыми миграциями Flyway; применённые миграции не редактируются.
- Таблицы БД называются во множественном числе: `countries`, `universities`, `language_tests`.
- Сборка — Gradle на Groovy DSL (`build.gradle`), не Kotlin DSL.

## Тесты

- Каждый важный бизнес-сценарий и ветка покрываются отдельным тестом с явными проверками.
- Косвенное покрытие (код выполнился в чужом тесте) не считается тестированием.
- Интеграционные тесты с БД и хранилищем — на Testcontainers.
- Задача не завершена, пока не прогнаны все тесты затронутых тестовых классов.

## Документация

- При изменении архитектуры, стека или структуры обновляй README в том же изменении; новое решение — новая строка в журнале решений (ADR).

## Задачи

- Задачи ведутся в GitHub Issues репозитория `4sq4r/serendipity`: эпики — этапы дорожной карты, стори — задачи внутри них.
- Создание, изменение и закрытие задач — через скилл `github-issues`.
- Перед началом работы найди соответствующую стори и прочитай её; если её нет — предложи создать.
- Ветка называется по номеру стори: `feature/<номер>-<кратко>`; PR закрывает стори через `Closes #<номер>`.

## Git

- Ветки: `epic/...`, `feature/...`, `fix/...`, `chore/...`.
- На каждый эпик — ветка от `main` с номером issue эпика: `epic/<номер>-<кратко>`, например `epic/2-catalog`.
- На каждую задачу — отдельная ветка с номером issue: `feature/<номер>-<кратко>`, например `feature/3-countries-universities`.
- Сообщения коммитов — в повелительном наклонении, кратко описывают изменение.
- Не коммить и не пушь без явной просьбы.
- Вместе с веткой эпика сразу открывается черновой PR эпика в `main` с `Closes` для эпика и всех его задач. PR задач эпика направляются в ветку эпика, а не в `main`. PR эпика переводится из черновика в готовый только после того, как в ветку эпика влиты PR всех его задач. Задача вне эпика оформляется PR в `main`.
- PR не вливаешь сам — это делает владелец репозитория.
